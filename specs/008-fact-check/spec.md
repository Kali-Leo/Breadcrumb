# Spec 008: 求真——学习对话的事实核查（dev-2 分支）

> 状态：待 Leo 审核。
> 背景：学习者最怕的不是不知道，而是把错的当成对的学进去——学错再纠正比第一次学对
> 成本高得多，而 AI 的错误恰恰"说得最像真的"。调研结论（2026-07-30）：现有开源方案
> 集中在通用事实核查（Loki/RefChecker/MiniCheck），教育产品只做"圈定教材内答题"，
> 针对自由学习对话的准确性保障是空白。技术路线：声明分解 + 证据检索（借鉴 Loki 流水线，
> TS 自研，见 ADR-0004）。

## 需求

1. **核查流水线**（无头包 `plugin-factcheck`）：AI 回复完成后，可选触发：
   - **声明提取**：用轻量模型从回复中提取"可核查的事实性声明"（合并 Loki 的
     checkworthiness 步骤：观点、代码示例、数学推导、比喻不提取——只核查事实）
   - **证据检索**：每条声明生成搜索查询 → 检索证据源 → 抓取并验证可访问
     （复用 F8 "fetch-and-verify" 原则）
   - **判定**：证据 + 声明 → 三态结论：`supported`（有佐证）/ `insufficient`
     （没找到佐证）/ `contradicted`（与佐证冲突），附证据链接
   - 一切 LLM 输出过 Zod 边界校验
2. **证据源抽象**：`EvidenceProvider` 接口，MVP 内置三个免 key 实现：
   Wikipedia REST API（学习场景概念性知识覆盖高）、必应中国 cn.bing.com
   （**大陆可达**——Wikipedia/DuckDuckGo 在大陆均不可访问）、DuckDuckGo 兜底；
   预留用户自配搜索 API（Serper/Tavily）的扩展位
   - **大陆网络适配**：所有证据请求带超时快速失败（被墙连接会挂死而非报错）；
     提供按网络环境选择的默认源链（大陆=仅 Bing，国际=Wikipedia 优先）；
     网络环境由设置页选择或启动时探测（T4）
3. **温柔呈现**（零压力红线）：
   - 消息旁一个安静的小标记，展开可见："这几点我找到了佐证（链接）"、
     "这一点我没找到佐证，值得再确认"
   - 永不出现"AI 错了 / 你学错了"式文案；`contradicted` 也只说
     "我查到的说法和这里不一致，两边都给你看"
   - 核查中不打断阅读，结果就绪后淡入
4. **开关与计价**（产品原则 2/3）：
   - 独立开关，默认关闭；开启后可选"逐条手动核查"或"每轮自动核查"
   - 所有 LLM 调用记入独立 purpose `factcheck`，状态栏分账可见
   - 网络总开关关闭时功能整体不可用，温和提示
5. **知识树联动（本 spec 只埋事件）**：核查完成广播 `factcheck:finished`
   （含逐声明结论），供未来把"已验证"标记挂上知识节点——通用核查工具做不到的差异化

## 验收标准

- [ ] 让 AI 回答一个含真实事实的问题（如"光速是多少"）→ 核查标记显示有佐证 + 可点开链接
- [ ] 诱导 AI 编造（如问一个不存在的人物/论文）→ 显示"没找到佐证"的温柔提示
- [ ] 界面任何地方不出现指责性文案；核查失败（断网/证据源超时）静默降级不报错弹窗
- [ ] 开关关闭时零 LLM 调用零网络请求；开启后状态栏能看到 factcheck 分账
- [ ] 证据链接全部实测可访问后才展示（fetch-and-verify）
- [ ] 声明提取、判定、证据验证有单元测试（mock LLM 与 fetch）；全部质量门通过

## 非目标（明确不做）

- 不核查代码正确性与数学推导（未来可接沙盒执行/形式化工具，另立 spec）
- 不做"教材圈定"模式（那是另一个功能方向）
- 不在本 spec 内做知识节点的"已验证"标记 UI（只埋事件）
